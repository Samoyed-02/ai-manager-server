## 실행한 작업을 대화 기록에 남기기 (#29)

**문제:** 대화 기록에는 답변 텍스트만 저장됐다. 그래서 다음 턴의 모델은 자기가 도구를 실행했다는 근거를 보지 못했다.
- 실제로 등록한 목표·활동·루틴을 "도구를 호출한 결과가 아니었다"고 정정했다.
- 검색해서 답한 날씨도 "검색 결과가 아니었다"고 정정했다.

**수정**
- V10: `messages.actions` (text, 한 줄에 작업 하나)
- 답변을 저장할 때 실행한 작업을 함께 저장한다.
  - 예: 활동 기록 요약, `문서 작업 생성: …`, `실패: …`, `조회: …`, `웹 검색 N회`, `웹 페이지 읽기 N회`
- 다음 요청에서는 이전 답변 앞에 `[서버 기록: 이 답변에서 실제로 실행한 작업]`을 붙인다.
- 프롬프트에 두 가지를 추가했다.
  - `[서버 기록]`은 직접 쓰지 말 것
  - 기록이 없는 예전 답변도 하지 않았다고 단정하지 말고, 필요하면 조회 도구로 확인할 것
- `GET /conversations/{id}/messages`가 `actions: [...]`를 내려 준다.

## 동적 필터링 웹 검색의 출처 (#30)

**문제 1: 출처가 붙지 않는다.**
- `web_search_20260209`는 모델이 코드 실행(`code_execution`) 안에서 `web_search`를 부르고, 결과를 코드로 걸러 쓴다.
- 이렇게 쓴 답변에는 인용(`web_search_result_location`)이 달리지 않는다.
- 출처를 인용에서만 모으고 있었으므로 목록이 비었다.

**문제 2: 응답 누적이 실패한다.**
- 서버 도구 블록이 입력 조각(`input_json_delta`) 없이 오면, SDK `MessageAccumulator`가 `Missing input JSON for index N`으로 실패한다.
- 그러면 `pause_turn`이 왔을 때 이어 받지 못한다.

**수정**
- 입력 조각 없이 끝난 도구 블록에는, 블록 시작 때 받은 입력을 조각으로 만들어 넣는다.
- 검색 결과 블록(`web_search_tool_result`)도 모은다. 인용이 없으면 **검색한 페이지**로 붙인다.
- 진단 로그 `chat.blocks`(debug)에 응답 블록 구성을 남긴다. 예:

  ```
  [server_tool_use:code_execution, server_tool_use:web_search, web_search_tool_result:9, code_execution_tool_result:encrypted, ..., thinking, text]
  ```

## 프롬프트 캐시 (#31)

**문제:** 모든 호출이 `cache_read_tokens=0`이었다. 채팅 요청 한 번의 입력이 약 1.1~1.3만 토큰인데, 매번 정가를 냈다.

**수정**
- 캐시는 tools → system → messages 순서의 앞부분이 같을 때만 읽힌다. 그래서 다음처럼 배치했다.
  - 고정 지시(앞의 도구 정의 포함)와 현재 사용자 메시지에 캐시 지점을 둔다. 유지 시간은 5분이다.
  - 매 턴 바뀌는 맥락(현재 시각, 기억, 활동 등)은 대화 기록 뒤의 system 메시지로 보낸다.
  - 다음 턴에는 대화 기록 전체를 캐시에서 읽는다.
- 같은 턴의 도구 라운드에서는 요청 최상위의 자동 캐시 지점을 쓴다.
- 대화 중 system 메시지가 문제를 일으키면 `claude.context-as-system-message=false`로 맥락을 예전 위치(시스템 프롬프트)로 되돌린다.

**결과** (같은 대화 4턴)

| 턴 | 캐시 읽기 | 비용 | 수정 전 |
|---|---|---|---|
| 첫 인사 | 0 | $0.029 | $0.025 |
| 활동 기록 | 33,657 | $0.012 | $0.051 |
| 목표 등록 | 22,722 | $0.010 | $0.058 |
| 목표에 연결된 활동 | 23,271 | $0.009 | $0.055 |

- 두 번째 턴부터 약 80% 줄었다.
- 첫 턴은 캐시 쓰기 비용 때문에 약 20% 비싸다.
- 5분 넘게 쉬면 다시 쓰기 비용이 든다. 1시간 유지로 바꿀지는 실제 사용 로그를 보고 정한다.

## 웹 검색 한도 (#32)

**문제:** 동적 필터링은 코드 한 번 안에서 검색을 연달아 부른다. 그래서 `max_uses=3`으로는 "이번 주 IT 뉴스 3개"가 두 번 다 실패했다.

**수정**
- 한도를 6회로 올렸다. 질문당 검색비는 최대 $0.06이다.
- 프롬프트에 "한도에 걸리면 이미 찾은 결과로 답하라"를 넣었다.
- 출처 지시에서 "서버가 처리한다"는 이유를 뺐다. 모델이 그 설명을 답변에 옮기던 문제가 사라졌다.

**결과**
- 뉴스 질문이 성공했다.
- 이후 점검에서 검색 횟수는 1, 2, 5, 6회였다. 6회 한도를 다 쓴 적이 있다.

## 검색한 페이지 고르기 (#33, #36)

**문제:** 인용이 없을 때 검색 결과를 받은 순서대로 5개를 붙였다. 그래서 무관한 페이지(Seoul City Hall 위키)나 포털 첫 화면(다음뉴스)이 들어갔다.

**수정** (`SearchResultPicker.kt`)
1. 사이트·섹션 첫 화면과 사이트 안 검색 결과 페이지를 먼저 뺀다(#36).
   - 검색 결과 페이지: 경로에 `search`가 있거나, 쿼리에 `q`·`query`·`keyword`가 있는 경우
2. 남은 결과 전체에서 제목과 답변을 두 글자 단위로 비교한다.
   - 겹침이 2개 이상이면서 제목의 20% 이상이면 통과한다. 통과한 것을 점수 순으로 최대 5개 붙인다.
   - AI, IT 같은 두 글자 영어 단어는 계산에서 뺀다. 첫 점검에서 "AI의 검색결과" 같은 페이지가 이 단어만으로 통과했기 때문이다.
3. 하나도 통과하지 못하면 앞쪽 3개를 붙인다. 검색 결과는 출처와 함께 보여야 하므로 목록을 비우지 않는다.

**결과**
- 뉴스 답변에 쓰인 기사가 모두 목록에 들어갔다.
- 한계 1: 모델이 "제외했다"고 한 날씨 페이지도, 제목이 겹치면 남는다.
- 한계 2: 경로가 짧은 실제 기사(예: `blog.com/ai-news`)는 첫 화면으로 보고 뺀다.

## 서버 도구 앞의 진행 문장 (#34)

**문제:** 뉴스 답변이 "Results are a JSON string; parse it.이번 주…"로 시작했다.
- 모델이 검색 코드 전에 낸 짧은 텍스트가 그대로 스트리밍되고 저장된 것으로 보인다.
- 문장 끝과 실제 답변 사이에 구분이 없어 붙어 나왔다.

**수정** (`InterimTextFilter.kt`)
1. 응답 시작이나 도구 바로 뒤에 혼자 나온 텍스트 블록은, 앞의 150자를 모아 두고 바로 보내지 않는다.
2. 그 안에서 블록이 끝나고 서버 도구(웹 검색, 코드 실행, 페이지 읽기)가 이어지면 버린다.
3. 버리지 않는 경우: 텍스트에 바로 이어진 블록, 인용이 달린 텍스트, 우리 서버 도구 앞의 문장
   - 처음 규칙으로는 인용 답변 중간의 짧은 문장(" 같은 기사.")까지 버려졌다. 기존 테스트가 이를 잡아서 이렇게 좁혔다.
4. 버릴지는 응답 하나 안에서만 정한다. 응답이 끝나면 모아 둔 텍스트는 그대로 보낸다.
5. 도구를 사이에 둔 텍스트는 빈 줄로 나눈다. 우리 서버 도구에도 적용되므로 "맡길게요." 다음 답변도 줄이 나뉜다.
6. 프롬프트에 "웹 검색이나 코드 실행 전에는 글을 쓰지 말고, 결과를 다 본 뒤 한 번에 답해"를 넣었다.
7. `chat.blocks` 로그에 텍스트 길이와 버림 여부를 남긴다. 예: `text:37:dropped`

**결과**
- 재점검 응답에는 도구 앞 텍스트가 없었다(버림 0건). 원인 추정과 버림 동작은 테스트로만 확인했다.
- 최종 답변이 짧은 텍스트 블록 13개로 나뉘어 와도 버려지지 않는 것은 실제 응답으로 확인했다.

## `HV000271` 경고 (#35)

- `VoiceCallRequest.turns`의 `@field:Valid List<VoiceTurn>`을 `List<@Valid VoiceTurn>`으로 바꿨다.
- Kotlin은 타입 인자에 붙은 어노테이션을 기본으로는 바이트코드에 남기지 않는다.
  - 그래서 위치만 바꾸면, 경고는 사라지지만 발화 검사도 함께 빠졌다.
  - 이때 `role: system`이 DB 제약에서야 막혔고, 기존 테스트가 이를 잡았다.
- `build.gradle.kts`에 `-Xemit-jvm-type-annotations`를 추가해 해결했다.
- 빈 발화 내용(`text`)이 400을 받는지 확인하는 테스트도 추가했다.
