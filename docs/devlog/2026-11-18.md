# 2026-11-18 개발 기록

데이터가 어디로 나가는지 확인하고 보안을 검토했다. 그 결과로 로그인 전체 잠금을 없애고(IP별 잠금만 남김), 채팅·통화 원문의 민감 정보를 받는 지점에서 가렸다.

## 데이터 외부 전송과 보안 검토

코드를 읽고 앞서 운영에서 확인한 것을 근거로 했다. 침투 테스트는 하지 않았다.

**외부로 나가는 데이터.** 서버가 직접 부르는 외부 서비스는 Anthropic API 하나다(`AnthropicConfig`).

| 어디로 | 무엇이 | 언제 |
|---|---|---|
| Anthropic | 채팅 질문, 최근 대화 40개, 맥락(기억, 목표, 루틴, 알림, 최근 대화 요약, 회고) | 채팅마다 |
| Anthropic | 통화 원문 전체 | 통화 뒤 기억 추출 |
| Anthropic | 기억, 목표, 활동 통계 | 브리핑, 주간 회고, 문서 작성 |
| 검색 엔진·웹사이트 (Claude를 거쳐) | 질문에서 만든 검색어, 읽을 페이지 주소 | 채팅의 웹 검색 |
| Google (Gemini Live) | 통화 음성. 웹 앱에서 바로 가고 서버를 거치지 않음 | 통화 중 |
| Railway | DB 전체(대화·통화 원문, 기억), 서버 로그 | 항상 |
| GitHub | 코드와 문서. 대화 내용 없음 | 푸시 |

서버 로그(`claude.usage`, `chat.blocks`)에는 토큰 수, 블록 종류, 길이만 남는다. 대화 내용을 찍는 로그는 없다. 로그인 실패 로그에는 IP와 기기 이름이 남는다.

**찾은 것** (위험 높은 순)

| # | 내용 | 처리 |
|---|---|---|
| 1 | 민감 정보 필터가 기억에만 적용됨. 통화·채팅 원문은 그대로 저장되고 Claude로 감 | 오늘 수정 (#52) |
| 2 | 읽은 웹 페이지의 숨은 지시로 모델이 우리 도구(루틴 삭제, 기억 저장 등)를 실행할 수 있음. 삭제 전 확인은 프롬프트 지시일 뿐 강제가 아님 | 남김 |

이미 갖춘 것:
- bcrypt 비밀번호와 일회용 TOTP, 해시로만 저장하는 세션 토큰
- IP별 시도 제한(IP 위조 불가 확인)
- 토큰 없는 API·관리 엔드포인트·모르는 출처의 CORS 차단(운영 확인)
- 커밋 기록에 비밀값 없음, 설정이 틀리면 기동 실패
- 모든 입력의 길이·형식 검증

확인하지 못한 것: Anthropic의 API 데이터 보관 기간, Railway 디스크 암호화 여부.

## 전체 로그인 잠금 제거

**문제:** 로그인 실패를 두 기준으로 막았다.
- 같은 IP에서 15분 안에 5번 실패하면 그 IP를 막는다.
- IP와 관계없이 15분 안에 실패가 50번이면 모든 로그인을 막는다.

두 번째 기준 때문에, 서버 주소를 아는 사람이 IP 10개로 5번씩 실패하면 본인도 15분 동안 새로 로그인할 수 없었다. 이미 로그인한 기기는 세션 토큰으로 계속 쓸 수 있어서, 영향은 새 기기 로그인과 만료된 세션에 한정됐다.

**결정:** 전체 기준을 지웠다.
- 로그인에는 12자 이상 비밀번호(bcrypt)와 30초마다 바뀌는 일회용 TOTP 코드가 함께 필요하다. IP 하나는 15분에 5번만 시도할 수 있다. IP를 많이 동원해도 두 값을 함께 맞힐 확률은 사실상 0이라, 전체 기준이 더하는 보안이 작았다.
- IP 위조가 통하지 않는 것은 11-07에 확인했다(`APP_TRUST_FORWARDED_FOR`). 그래서 IP별 기준은 그대로 믿을 수 있다.
- 다른 방안으로, 최근 성공한 IP는 전체 잠금에서 빼 주는 방식도 검토했다. 코드가 늘고, 휴대폰처럼 IP가 자주 바뀌면 본인도 막힐 수 있어 고르지 않았다.

**변경**
- `AuthService`: `MAX_FAILURES_TOTAL`을 지웠다. `lockedFor()`는 IP별 조회만 한다.
- `AuthApiTest`: 다른 IP 12개의 실패 60건을 넣고, 새 IP의 정상 로그인이 200인지 확인한다. 전체 잠금이 되살아나면 실패한다.
- `login_attempts(created_at)` 인덱스는 30일 지난 기록 정리에도 쓰여 그대로 뒀다.
- API 응답(429, `Retry-After`)은 그대로다.

**확인:** 테스트 175개 모두 통과(통합 129, 단위 46).

## 민감 정보를 받는 지점에서 가리기

**문제:** 민감 정보 필터(`SensitiveInfoFilter`)는 기억을 저장할 때만 썼다. 통화 원문과 채팅 질문은 받은 그대로 DB(`messages`)에 저장됐고, 그 원문이 Claude로 갔다(통화는 기억 추출 때, 채팅은 대화 기록으로). "와이파이 비밀번호는 저장하지 않는다"는 기억에 대해서만 사실이었다.

**변경**
- `SensitiveInfoFilter.redact()`: 같은 규칙에 걸리는 부분만 `[가림]`으로 바꾼다.
  - 하이픈 카드번호를 계좌 규칙이 앞 12자리만 가리면 끝 4자리가 남는다. 그래서 카드 규칙을 먼저 적용한다.
- `isSensitive()`는 `redact(text) != text`로 바꿨다. 규칙이 한 곳에만 있다.
- 통화 원문(`VoiceCallController`)과 채팅 질문(`ChatService.prepare`)을 저장하기 전에 가린다. Claude 요청은 저장된 값으로 만들므로 함께 가려진다.

**대가**
- 일부러 알려 준 번호도 Claude에게는 `[가림]`으로 보인다.
- 32자 이상 영문·숫자 문자열 규칙이 URL 안의 긴 ID를 가릴 수 있다.
- 새로고침하면 대화 기록에 `[가림]`으로 보인다. API 형식은 그대로다.

**하지 않은 것**
- 이미 저장된 메시지는 고치지 않았다.
- 프로필, 루틴·목표 제목, 활동 메모는 필터 밖이다.
- 통화 음성은 웹 앱에서 Gemini로 바로 가므로 이 수정과 무관하다.

**확인:** 테스트 184개 모두 통과. 가리기 7개, 통화 저장, 채팅 저장과 Claude 요청 테스트를 추가했다.
