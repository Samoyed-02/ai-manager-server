## 문제

`claimNext()`는 `FOR UPDATE SKIP LOCKED`로 작업을 가져오기 때문에 가져오는 단계 자체는 안전했다. 문제는 처리 결과를 저장하는 단계였다.

1. **소유권 확인 없음**: `recoverStale()`은 10분 넘게 `RUNNING`인 작업을 `PENDING`으로 되돌린다. 원래 워커가 아직 Claude 응답을 기다리는 중이어도 되돌리기 때문에, 다른 워커가 같은 작업을 다시 가져가 두 워커가 각각 문서를 저장했다. Anthropic SDK 기본 타임아웃이 약 10분이라 실제로 일어날 수 있는 상황이다.
2. **두 번에 나뉜 저장**: `documents.save`가 먼저 커밋되고 `tasks.save`가 따로 실행됐다. 그 사이에 실패하거나 서버가 죽으면 문서는 남고 작업은 `RUNNING`으로 남아, 복구 후 재실행되면서 문서가 하나 더 생겼다.
3. **예전 엔티티로 덮어쓰기**: 마지막 `tasks.save(task)`가 처리 시작 시점의 엔티티를 병합해서, 다른 워커가 올린 `attempts`와 상태를 덮어썼다.
4. **DB 제약 없음**: `documents.task_id`에 unique 제약이 없었다.

중복이 생기면 `findByTaskId`가 `IncorrectResultSizeDataAccessException`을 던져 `GET /tasks/{id}`가 500을 반환했다.

## PORT 환경변수 처리

2026-10-07 `bf32609` 커밋은 메시지와 달리 `server.port: 8080` 고정값이라 `PORT` 환경변수가 반영되지 않았다 (Spring이 자동으로 읽는 건 `SERVER_PORT`뿐). Render, Railway, Cloud Run처럼 `PORT`로 포트를 지정하는 플랫폼에서는 서버가 엉뚱한 포트에서 뜬다.

- `application.yml`: `server.port: ${PORT:8080}`
  - `PORT`가 있으면 그 값, 없으면 8080 (로컬과 기존 Docker 실행은 그대로)
  - `SERVER_PORT`를 주면 여전히 `PORT`보다 우선
- 확인: `PORT=9090 ./gradlew bootRun` → 9090에서 기동, `PORT` 없이 실행 → 8080에서 기동

## Task용 Claude 호출 타임아웃 제한

소유권 확인으로 중복 문서는 막았지만, Claude 호출이 stale 기준(10분)보다 오래 걸리면 정상 처리 중인 작업이 복구되어 Claude를 한 번 더 호출하는 낭비는 남아 있었다. SDK(2.60.0) 기본값은 non-streaming 타임아웃이 `maxTokens`에 따라 30초~10분이고, 타임아웃도 재시도하며 `maxRetries`가 2라서 최악의 경우 한 호출이 30분 가까이 걸릴 수 있었다.

- `TaskWorker.runClaude()`: `client.withOptions { it.timeout(4분).maxRetries(1) }`로 Task 호출에만 적용
  - 최악 약 8분(4분 × 2회 + 재시도 대기) < 10분
  - SDK 재시도를 줄여도 Task 단계에서 최대 3회 재시도가 있다
  - 채팅(`ChatService`)과 공유하는 클라이언트라 전역 설정은 건드리지 않음
- `STALE_AFTER`, `CLAUDE_TIMEOUT`, `CLAUDE_MAX_RETRIES` 상수로 정리하고 `recoverStale()`도 `STALE_AFTER`를 쓰도록 변경
- `init`에서 `CLAUDE_TIMEOUT × (CLAUDE_MAX_RETRIES + 1) < STALE_AFTER`를 검사해, 값을 잘못 바꾸면 서버가 기동하지 않음
- 테스트: `AnthropicClient` mock을 `Answers.RETURNS_SELF`로 바꿔 `withOptions(...)`가 mock 자신을 돌려주게 함
- 한계: 실제 API로 타임아웃이 나는 상황은 확인하지 못했다. 설정 관계는 위 `init` 검사로 보장한다.

## 잘리거나 거절된 Claude 응답 처리

점검 문서 1번. `runClaude()`가 응답 텍스트를 그대로 돌려줘서, 8192 토큰에서 잘린 문서(`max_tokens`)나 거절 응답(`refusal`)도 `DONE` 문서로 저장됐다.

- `stop_reason`에 따라 처리를 나눈다

| `stop_reason` | 처리 |
|---|---|
| `end_turn`, `stop_sequence` + 본문 있음 | 정상 저장 (`DONE`) |
| `end_turn`, `stop_sequence` + 본문 없음 | 실패, 재시도 (`PENDING`) |
| `max_tokens` | 재시도 없이 `FAILED` |
| `refusal` | 재시도 없이 `FAILED` |
| 그 외 (`tool_use`, 컨텍스트 초과 등) 또는 없음 | 재시도 없이 `FAILED` |

- 같은 요청을 다시 보내면 대부분 같은 결과라서, 잘림·거절은 재시도하지 않는다. `NonRetryableTaskException`으로 구분하고 `fail(claim, error, retryable)`이 retryable이 false면 남은 시도 횟수와 상관없이 `FAILED`와 `finished_at`을 기록한다.
- `tasks.error`에 원인을 남긴다: `출력 한도(8192 토큰)에 도달해 문서가 잘림 (output_tokens=…)`, `Claude가 요청을 거절함 (category=…)`
- `maxTokens(8192)`는 그대로 두었다. `error`에 잘림이 기록되니, 실제 빈도를 본 뒤 한도 상향(+ streaming 전환)을 정한다.
- 테스트
  - mock 헬퍼를 `ClaudeMocks.kt`로 분리하고 `stop_reason`, `usage`, 거절 category를 stub할 수 있게 함 (기존 mock은 `stopReason()`이 빈 값이라 새 검사에 걸림)
  - `TaskWorkerStopReasonTest`: 잘림 → `FAILED`(attempts 1, 문서 없음), 거절 → `FAILED`(category 기록), 빈 본문 → `PENDING`
  - 전체 7개 통과
- 범위 밖: 거절 시 다른 모델로 재요청하는 server-side `fallbacks`(beta)는 실제 거절 빈도를 본 뒤 검토. 채팅의 `stop_reason` 확인은 점검 문서 2번에서 처리.

|---|---|
| 정상 종료 | assistant 저장 (`COMPLETE`) |

## 오류 원문 숨기기와 재시도 구분

점검 문서 7번과 9번의 남은 부분. 채팅 `error` 이벤트와 `tasks.error`(`GET /tasks`)에 예외 원문이 그대로 나갔다. 로컬 실행에서 `{"message":"401: {\"type\":\"error\",...\"invalid x-api-key\"...,\"request_id\":\"req_...\"}"}`가 클라이언트로 가는 것을 확인했다. 또 401·400처럼 다시 해도 같은 결과인 오류도 Task에서 3번 재시도했다.

- `claude/ClaudeErrors.kt`: `classifyClaudeError(e)`가 SDK 예외 타입과 `statusCode()`로 종류를 정한다

| 종류 | 기준 | 사용자 문구 | 재시도 |
|---|---|---|---|
| `CONFIG` | 401, 403, 404, 자격 증명 없음 | 서버 설정 문제로 처리할 수 없습니다 | 안 함 |
| `BAD_REQUEST` | 400, 413, 422 | 요청을 처리할 수 없습니다 (입력이 너무 길거나 형식 문제) | 안 함 |
| `RATE_LIMITED` | 429 | 요청이 많아요. 잠시 후 다시 시도해 주세요 | 함 |
| `UNAVAILABLE` | 5xx, 529, 스트리밍 중 error 이벤트(`SseException`) | AI 서비스가 일시적으로 불안정합니다 | 함 |
| `NETWORK` | `AnthropicIoException`, `IOException`(타임아웃 포함) | AI 서비스 연결에 실패했습니다 | 함 |
| `UNKNOWN` | 그 밖의 예외 (DB 오류 등) | 처리 중 오류가 발생했습니다 | 함 |

- 채팅: `error` 이벤트를 `{"code", "message"}`로 바꿨다 (`code` 추가). 직접 만든 오류는 `REFUSED`, `EMPTY_RESPONSE` 코드를 쓴다.
- Task: `tasks.error`에는 사용자 문구만 저장하고, 종류의 `retryable`에 따라 재시도 여부를 정한다. 직접 판정한 실패(잘림, 거절, 빈 본문)는 원래 안전한 문구라 그대로 저장한다. 이를 위해 `NonRetryableTaskException`을 `TaskFailureException(message, retryable)`로 일반화했다.
- 원문(상태 코드, 응답 본문, `request_id`, 스택)은 서버 로그에만 남는다. 로컬 실행에서 클라이언트는 `{"code":"CONFIG","message":"서버 설정 문제로 처리할 수 없습니다"}`를 받고, 로그에는 `UnauthorizedException: 401: {...,"request_id":"req_..."}`가 남는 것을 확인했다.
- 이미 저장된 `tasks.error` 값은 바꾸지 않았다. 새로 생기는 실패부터 적용된다.
- 테스트: `ClaudeErrorsTest` 3개(분류, 재시도 여부), `ChatServiceTest` 1개(429 → `RATE_LIMITED`, 원문 미포함), Task 2개(401 → 바로 `FAILED`, 429 → `PENDING`, 둘 다 사용자 문구만 저장). 기존 채팅 테스트 2개는 기대값을 사용자 문구로 바꿨다. 전체 20개 통과.

## 문서 조회 최적화

점검 문서 3·4번. `ContextService`는 채팅과 작업마다 본문(`content`)까지 포함한 문서 50개를 읽고 제목 5~10개만 썼고, `GET /documents`도 본문까지 읽었다. `GET /tasks`는 `DONE` 작업마다 문서를 따로 조회했다(최대 20번, 매번 본문 포함).

- `DocumentRepository`에 인터페이스 projection을 도입했다. SQL이 projection의 컬럼만 `select`한다.
  - `DocumentSummary`(id, taskId, title, createdAt): `findAllByOrderByCreatedAtDesc(Limit)` → 컨텍스트, `GET /documents`
  - `DocumentRef`(id, taskId): `findByTaskIdIn(ids)` → `GET /tasks`, `findRefByTaskId(id)` → `GET /tasks/{id}`
  - 쓰지 않게 된 `findTop50ByOrderByCreatedAtDesc()`, `findByTaskId()`는 삭제
- `GET /tasks`: 작업 20개를 읽은 뒤 `DONE` 작업 ID로 문서 ID를 한 번에 조회해 맵으로 채운다. V3의 `task_id` unique 덕분에 키가 겹치지 않는다.
- `V5__documents_created_at_index.sql`: `documents(created_at desc)` 인덱스. 최근 문서 N개 조회가 채팅·작업마다 실행되므로 추가했다.
- API 응답 형식은 그대로다.
- 확인
  - `TaskControllerTest` 3개: `GET /tasks`(DONE 5 + PENDING 2)에서 SQL 문 **2개**, `GET /documents` 최신순 50개, 컨텍스트에 최근 제목 10개. 전체 23개 통과.
  - SQL 문 수는 Hibernate `Statistics.prepareStatementCount`로 센다. 테스트 프로필에만 `hibernate.generate_statistics: true`를 켰다.
  - 테스트 컨테이너에서 SQL 로그로 본문을 읽지 않는 것을 확인했다.
    - `select d1_0.id,d1_0.task_id,d1_0.title,d1_0.created_at from documents d1_0 order by d1_0.created_at desc fetch first ? rows only`
    - `select d1_0.id,d1_0.task_id from documents d1_0 where d1_0.task_id in (?,?,?,?,?)`
  - `findRefByTaskId`는 테스트가 없지만, Spring Data가 기동할 때 메서드 이름으로 만든 쿼리를 검증하므로 쿼리 자체는 유효하다.
- 이번에는 로컬 개발 DB로 서버를 띄우지 않아서, V5는 아직 로컬 DB에 적용되지 않았다.
