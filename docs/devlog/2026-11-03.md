## 문제

`claimNext()`는 `FOR UPDATE SKIP LOCKED`로 작업을 가져오기 때문에 가져오는 단계 자체는 안전했다. 문제는 처리 결과를 저장하는 단계였다.

1. **소유권 확인 없음**: `recoverStale()`은 10분 넘게 `RUNNING`인 작업을 `PENDING`으로 되돌린다. 원래 워커가 아직 Claude 응답을 기다리는 중이어도 되돌리기 때문에, 다른 워커가 같은 작업을 다시 가져가 두 워커가 각각 문서를 저장했다. Anthropic SDK 기본 타임아웃이 약 10분이라 실제로 일어날 수 있는 상황이다.
2. **두 번에 나뉜 저장**: `documents.save`가 먼저 커밋되고 `tasks.save`가 따로 실행됐다. 그 사이에 실패하거나 서버가 죽으면 문서는 남고 작업은 `RUNNING`으로 남아, 복구 후 재실행되면서 문서가 하나 더 생겼다.
3. **예전 엔티티로 덮어쓰기**: 마지막 `tasks.save(task)`가 처리 시작 시점의 엔티티를 병합해서, 다른 워커가 올린 `attempts`와 상태를 덮어썼다.
4. **DB 제약 없음**: `documents.task_id`에 unique 제약이 없었다.

중복이 생기면 `findByTaskId`가 `IncorrectResultSizeDataAccessException`을 던져 `GET /tasks/{id}`가 500을 반환했다.

## PORT 환경변수 처리

2026-10-07 `bf32609` 커밋은 메시지와 달리 `server.port: 8080` 고정값이라 `PORT` 환경변수가 반영되지 않았다 (Spring이 자동으로 읽는 건 `SERVER_PORT`뿐). Render, Railway, Cloud Run처럼 `PORT`로 포트를 지정하는 플랫폼에서는 서버가 엉뚱한 포트에서 뜬다.

- `application.yml`: `server.port: ${PORT:8080}`
  - `PORT`가 있으면 그 값, 없으면 8080 (로컬과 기존 Docker 실행은 그대로)
  - `SERVER_PORT`를 주면 여전히 `PORT`보다 우선
- 확인: `PORT=9090 ./gradlew bootRun` → 9090에서 기동, `PORT` 없이 실행 → 8080에서 기동

## Task용 Claude 호출 타임아웃 제한

소유권 확인으로 중복 문서는 막았지만, Claude 호출이 stale 기준(10분)보다 오래 걸리면 정상 처리 중인 작업이 복구되어 Claude를 한 번 더 호출하는 낭비는 남아 있었다. SDK(2.60.0) 기본값은 non-streaming 타임아웃이 `maxTokens`에 따라 30초~10분이고, 타임아웃도 재시도하며 `maxRetries`가 2라서 최악의 경우 한 호출이 30분 가까이 걸릴 수 있었다.

- `TaskWorker.runClaude()`: `client.withOptions { it.timeout(4분).maxRetries(1) }`로 Task 호출에만 적용
  - 최악 약 8분(4분 × 2회 + 재시도 대기) < 10분
  - SDK 재시도를 줄여도 Task 단계에서 최대 3회 재시도가 있다
  - 채팅(`ChatService`)과 공유하는 클라이언트라 전역 설정은 건드리지 않음
- `STALE_AFTER`, `CLAUDE_TIMEOUT`, `CLAUDE_MAX_RETRIES` 상수로 정리하고 `recoverStale()`도 `STALE_AFTER`를 쓰도록 변경
- `init`에서 `CLAUDE_TIMEOUT × (CLAUDE_MAX_RETRIES + 1) < STALE_AFTER`를 검사해, 값을 잘못 바꾸면 서버가 기동하지 않음
- 테스트: `AnthropicClient` mock을 `Answers.RETURNS_SELF`로 바꿔 `withOptions(...)`가 mock 자신을 돌려주게 함
- 한계: 실제 API로 타임아웃이 나는 상황은 확인하지 못했다. 설정 관계는 위 `init` 검사로 보장한다.

## 잘리거나 거절된 Claude 응답 처리

점검 문서 1번. `runClaude()`가 응답 텍스트를 그대로 돌려줘서, 8192 토큰에서 잘린 문서(`max_tokens`)나 거절 응답(`refusal`)도 `DONE` 문서로 저장됐다.

- `stop_reason`에 따라 처리를 나눈다

| `stop_reason` | 처리 |
|---|---|
| `end_turn`, `stop_sequence` + 본문 있음 | 정상 저장 (`DONE`) |
| `end_turn`, `stop_sequence` + 본문 없음 | 실패, 재시도 (`PENDING`) |
| `max_tokens` | 재시도 없이 `FAILED` |
| `refusal` | 재시도 없이 `FAILED` |
| 그 외 (`tool_use`, 컨텍스트 초과 등) 또는 없음 | 재시도 없이 `FAILED` |

- 같은 요청을 다시 보내면 대부분 같은 결과라서, 잘림·거절은 재시도하지 않는다. `NonRetryableTaskException`으로 구분하고 `fail(claim, error, retryable)`이 retryable이 false면 남은 시도 횟수와 상관없이 `FAILED`와 `finished_at`을 기록한다.
- `tasks.error`에 원인을 남긴다: `출력 한도(8192 토큰)에 도달해 문서가 잘림 (output_tokens=…)`, `Claude가 요청을 거절함 (category=…)`
- `maxTokens(8192)`는 그대로 두었다. `error`에 잘림이 기록되니, 실제 빈도를 본 뒤 한도 상향(+ streaming 전환)을 정한다.
- 테스트
  - mock 헬퍼를 `ClaudeMocks.kt`로 분리하고 `stop_reason`, `usage`, 거절 category를 stub할 수 있게 함 (기존 mock은 `stopReason()`이 빈 값이라 새 검사에 걸림)
  - `TaskWorkerStopReasonTest`: 잘림 → `FAILED`(attempts 1, 문서 없음), 거절 → `FAILED`(category 기록), 빈 본문 → `PENDING`
  - 전체 7개 통과
- 범위 밖: 거절 시 다른 모델로 재요청하는 server-side `fallbacks`(beta)는 실제 거절 빈도를 본 뒤 검토. 채팅의 `stop_reason` 확인은 점검 문서 2번에서 처리.

## 채팅 실패 시 기록 정리

점검 문서 2번. 사용자 메시지는 먼저 저장하고 assistant 응답은 스트리밍이 끝난 뒤에만 저장해서, Claude 오류·SSE 타임아웃(180초)·브라우저 연결 끊김이 생기면 사용자 메시지만 남고 화면에서 본 부분 응답은 사라졌다. 채팅도 `stop_reason`을 확인하지 않았다.

- 스트리밍 흐름을 `ChatController`에서 `ChatService.respond(prepared, sink)`로 옮겼다. 컨트롤러는 `ChatEvent`를 SSE 이벤트로 바꿔 보내기만 한다. SSE 없이 서비스만으로 테스트할 수 있게 하려는 목적.
- 결과 처리

| 상황 | 처리 |
|---|---|
| 정상 종료 | assistant 저장 (`COMPLETE`) |
| `max_tokens` | 저장 (`TRUNCATED`) |
| 거절 + 텍스트 있음 | 저장 (`REFUSED`) |
| 텍스트 전에 실패 / 텍스트 없는 거절 | 사용자 메시지 삭제, 이번 요청으로 만든 대화면 대화도 삭제, `error` 이벤트 |
| 스트리밍 도중 오류 | 부분 응답 저장 (`INTERRUPTED`), `error` 이벤트 |
| 연결 끊김 / SSE 타임아웃 | 전송만 멈추고 끝까지 받아 저장 (`COMPLETE`) |

- 연결이 끊겼을 때 생성을 멈추지 않고 끝까지 받기로 했다. 모바일에서 화면이 꺼지거나 탭을 닫았다 열어도 전체 답변이 남고, 비용은 끝까지 봤을 때와 같다(`maxTokens` 4096). "생성 중지" API가 없어서 연결 끊김을 사용자가 일부러 멈춘 것으로 볼 근거가 약했다.
- `V4__message_status.sql`: `messages.status` (`COMPLETE`/`TRUNCATED`/`REFUSED`/`INTERRUPTED`, 기존 행은 `COMPLETE`). `tasks.status`와 맞춰 대문자로 저장한다.
- API 변경 (필드 추가만): `GET /conversations/{id}/messages`의 `status`, `done` 이벤트 데이터 `{}` → `{"status": ...}`
- `TRUNCATED`·`REFUSED`·`INTERRUPTED` 메시지도 사용자가 실제로 본 내용이라 다음 요청 히스토리에 그대로 넣는다.
- 테스트: `ChatServiceTest` 7개 (정상, 잘림, 새 대화에서 텍스트 전 실패, 기존 대화에서 텍스트 전 실패, 도중 실패, 연결 끊김, 텍스트 없는 거절). 전체 14개 통과.

- 프론트엔드 참고: 텍스트 전에 실패하면 사용자 메시지가 DB에서 지워지므로, `error` 이벤트를 받으면 입력 내용을 남겨 두는 것이 좋다.

## 오류 원문 숨기기와 재시도 구분

점검 문서 7번과 9번의 남은 부분. 채팅 `error` 이벤트와 `tasks.error`(`GET /tasks`)에 예외 원문이 그대로 나갔다. 로컬 실행에서 `{"message":"401: {\"type\":\"error\",...\"invalid x-api-key\"...,\"request_id\":\"req_...\"}"}`가 클라이언트로 가는 것을 확인했다. 또 401·400처럼 다시 해도 같은 결과인 오류도 Task에서 3번 재시도했다.

- `claude/ClaudeErrors.kt`: `classifyClaudeError(e)`가 SDK 예외 타입과 `statusCode()`로 종류를 정한다

| 종류 | 기준 | 사용자 문구 | 재시도 |
|---|---|---|---|
| `CONFIG` | 401, 403, 404, 자격 증명 없음 | 서버 설정 문제로 처리할 수 없습니다 | 안 함 |
| `BAD_REQUEST` | 400, 413, 422 | 요청을 처리할 수 없습니다 (입력이 너무 길거나 형식 문제) | 안 함 |
| `RATE_LIMITED` | 429 | 요청이 많아요. 잠시 후 다시 시도해 주세요 | 함 |
| `UNAVAILABLE` | 5xx, 529, 스트리밍 중 error 이벤트(`SseException`) | AI 서비스가 일시적으로 불안정합니다 | 함 |
| `NETWORK` | `AnthropicIoException`, `IOException`(타임아웃 포함) | AI 서비스 연결에 실패했습니다 | 함 |
| `UNKNOWN` | 그 밖의 예외 (DB 오류 등) | 처리 중 오류가 발생했습니다 | 함 |

- 채팅: `error` 이벤트를 `{"code", "message"}`로 바꿨다 (`code` 추가). 직접 만든 오류는 `REFUSED`, `EMPTY_RESPONSE` 코드를 쓴다.
- Task: `tasks.error`에는 사용자 문구만 저장하고, 종류의 `retryable`에 따라 재시도 여부를 정한다. 직접 판정한 실패(잘림, 거절, 빈 본문)는 원래 안전한 문구라 그대로 저장한다. 이를 위해 `NonRetryableTaskException`을 `TaskFailureException(message, retryable)`로 일반화했다.
- 원문(상태 코드, 응답 본문, `request_id`, 스택)은 서버 로그에만 남는다. 로컬 실행에서 클라이언트는 `{"code":"CONFIG","message":"서버 설정 문제로 처리할 수 없습니다"}`를 받고, 로그에는 `UnauthorizedException: 401: {...,"request_id":"req_..."}`가 남는 것을 확인했다.
- 이미 저장된 `tasks.error` 값은 바꾸지 않았다. 새로 생기는 실패부터 적용된다.
- 테스트: `ClaudeErrorsTest` 3개(분류, 재시도 여부), `ChatServiceTest` 1개(429 → `RATE_LIMITED`, 원문 미포함), Task 2개(401 → 바로 `FAILED`, 429 → `PENDING`, 둘 다 사용자 문구만 저장). 기존 채팅 테스트 2개는 기대값을 사용자 문구로 바꿨다. 전체 20개 통과.

## 문서 조회 최적화

점검 문서 3·4번. `ContextService`는 채팅과 작업마다 본문(`content`)까지 포함한 문서 50개를 읽고 제목 5~10개만 썼고, `GET /documents`도 본문까지 읽었다. `GET /tasks`는 `DONE` 작업마다 문서를 따로 조회했다(최대 20번, 매번 본문 포함).

- `DocumentRepository`에 인터페이스 projection을 도입했다. SQL이 projection의 컬럼만 `select`한다.
  - `DocumentSummary`(id, taskId, title, createdAt): `findAllByOrderByCreatedAtDesc(Limit)` → 컨텍스트, `GET /documents`
  - `DocumentRef`(id, taskId): `findByTaskIdIn(ids)` → `GET /tasks`, `findRefByTaskId(id)` → `GET /tasks/{id}`

- `GET /tasks`: 작업 20개를 읽은 뒤 `DONE` 작업 ID로 문서 ID를 한 번에 조회해 맵으로 채운다. V3의 `task_id` unique 덕분에 키가 겹치지 않는다.
- `V5__documents_created_at_index.sql`: `documents(created_at desc)` 인덱스. 최근 문서 N개 조회가 채팅·작업마다 실행되므로 추가했다.
- API 응답 형식은 그대로다.
- 확인
  - `TaskControllerTest` 3개: `GET /tasks`(DONE 5 + PENDING 2)에서 SQL 문 **2개**, `GET /documents` 최신순 50개, 컨텍스트에 최근 제목 10개. 전체 23개 통과.

  - 테스트 컨테이너에서 SQL 로그로 본문을 읽지 않는 것을 확인했다.
    - `select d1_0.id,d1_0.task_id,d1_0.title,d1_0.created_at from documents d1_0 order by d1_0.created_at desc fetch first ? rows only`
    - `select d1_0.id,d1_0.task_id from documents d1_0 where d1_0.task_id in (?,?,?,?,?)`
  - `findRefByTaskId`는 테스트가 없지만, Spring Data가 기동할 때 메서드 이름으로 만든 쿼리를 검증하므로 쿼리 자체는 유효하다.

## 컨테이너 실행 사용자와 profile 모듈 정리

점검 문서 11번, 12번 나머지.

### Dockerfile: root가 아닌 사용자로 실행
- 실행 단계(`eclipse-temurin:21-jre`)에 `USER`가 없어 앱이 root로 돌았다. 앱에 취약점이 생기면 컨테이너 안에서 root 권한을 그대로 쓰게 된다.
- `app` 사용자(uid/gid 10001, 로그인 셸 없음)를 만들고 `USER 10001:10001`로 실행한다. 이름이 아닌 숫자 UID라 Kubernetes `runAsNonRoot` 검사도 통과한다.
- `app.jar`는 `--chown=app:app`으로 복사한다. 앱은 디스크에 쓰지 않고 Tomcat 임시 디렉터리는 `/tmp`라 권한 문제는 없다.
- root가 아니면 1024 미만 포트에 바인딩할 수 없지만, 기본 8080과 플랫폼이 주는 `PORT`는 그 이상이라 영향이 없다.
- 확인 (로컬 개발 DB는 쓰지 않고 임시 리소스만 사용)
  - `docker build` 성공 (처음 빌드라 Gradle 의존성 다운로드에 몇 분 걸림)
  - `id` → `uid=10001(app) gid=10001(app)`, `app.jar` 소유자 `app`
  - 임시 네트워크에 임시 Postgres 17과 앱 컨테이너를 띄움: 마이그레이션 5개(V1~V5) 적용, `Tomcat started`, PID 1 `java -jar app.jar`가 `app` 사용자로 실행, `GET /tasks` 패스코드 없음 401 / 있음 200
  - 확인 후 임시 컨테이너·네트워크·이미지 삭제

## Postgres 버전 통일

점검 문서 10번. 개발(`compose.yaml`)은 `postgres:17`, 테스트(Testcontainers)는 `postgres:16-alpine`이라 테스트가 개발과 다른 버전에서 돌았다.

- 저장소에 배포 설정 파일이 없어 운영 DB 버전은 알 수 없었고, 아직 정해지지 않은 상태라 개발에 맞춰 **17로 통일**했다.
  - 개발을 16으로 내리는 방법도 있었지만, 로컬 개발 DB가 이름 없는 볼륨에 PG 17 형식으로 데이터를 갖고 있어 메이저 버전을 낮추면 컨테이너가 뜨지 않는다. 그 경우 `pg_dump`로 옮겨야 한다.
- `TestcontainersConfiguration`: `postgres:16-alpine` → `postgres:17-alpine`
- `compose.yaml`, `TestcontainersConfiguration`: 개발·테스트·운영이 같은 메이저 버전을 쓴다는 주석과, 낮출 때 `pg_dump`가 필요하다는 주의를 남겼다. `compose.yaml`은 주석만 바뀌어 로컬 DB 컨테이너에는 영향이 없다.
- 파일을 다시 컴파일하면서 드러난 기존 경고도 정리했다: Testcontainers 2에서 deprecated된 `org.testcontainers.containers.PostgreSQLContainer`를 `org.testcontainers.postgresql.PostgreSQLContainer`로 바꿨다.
- 확인: 전체 39개 통과, 테스트 로그에서 `postgres:17-alpine` 사용 확인, 경고 없음. 컨테이너 실행 사용자를 확인할 때(#11)도 임시 Postgres 17에서 마이그레이션 5개가 모두 적용됐다.
- 운영 DB를 정할 때 17이 아니면 `compose.yaml`과 `TestcontainersConfiguration`을 함께 바꾼다.

- 헬스체크 경로가 없고 모든 경로가 패스코드를 요구한다. 배포 플랫폼이 정해지면 다시 본다.
- `ALLOWED_ORIGINS` 기본값이 `http://localhost:3000`, 컨테이너 JVM 기본 힙이 메모리의 25%라는 점도 체크리스트에 적었다.

확인:

- 전체 테스트 40개 통과.
- 실제 이미지를 빌드해 임시 Postgres 17과 체크리스트의 환경변수만으로 실행했다.
  - `APP_PASSCODE=` → `APP_PASSCODE must not be blank`로 기동 실패
  - DB 환경변수 없음 → 기동 실패
  - 정상 실행 → V1~V5 적용, 패스코드 없음 401 / 있음 200, `ALLOWED_ORIGINS`의 origin preflight 200, `localhost:3000` preflight 403, `uid=10001(app)`
- 임시 컨테이너, 네트워크, 이미지는 확인 후 삭제했다.

## Claude 사용량 로그

남은 검토 항목(Task `maxTokens` 상향, 거절 시 `fallbacks`, 토큰 기준 히스토리 자르기)은 모두 "실제 빈도를 보고 정한다"였는데, 정상 호출의 `stop_reason`과 토큰 수를 남기지 않아 판단할 근거가 없었다. Claude 호출마다 `claude.usage` 로거에 한 줄을 남기게 했다 (`claude/ClaudeCallLog.kt`).

```
claude call kind=task id=<taskId> model=claude-sonnet-5-5 stop_reason=max_tokens input_tokens=3000
  output_tokens=8192 cache_read_tokens=- cache_creation_tokens=- duration_ms=41230 error=-
```

- **Task:** 응답을 받은 직후, `stop_reason` 검사 전에 남겨서 잘림·거절로 실패하는 호출도 기록된다. 호출이 예외로 끝나면 토큰 없이 `error=<ClaudeErrorKind>`만 남긴다.
- **채팅:** 입력 토큰은 `message_start`, 누적 출력 토큰은 `message_delta`에서 모은다. 스트림이 끝나면 정상·실패·빈 응답 모두 한 줄을 남기고, 채팅에만 `history_messages`(보낸 메시지 수)를 붙인다. 클라이언트 연결이 끊겨도 응답을 끝까지 받으므로 토큰 수가 그대로 남는다.
- 프롬프트와 응답 본문은 남기지 않는다(사용자 프로필·대화 내용).
- 같은 값을 SLF4J key-value로도 넣었다. `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs`면 JSON 필드가 되고, 토큰 수와 `duration_ms`는 숫자로 나온다. 알 수 없는 값(`-`)은 필드에서 빠진다. 배포 체크리스트의 선택 환경변수에 추가했다.
- DB 저장(`claude_calls` 테이블)은 하지 않았다. 배포 플랫폼의 로그 보관 기간이 짧으면 그때 추가한다.

로그로 판단할 것:

| 검토 항목 | 볼 값 |
|---|---|
| Task `maxTokens` 상향·streaming 전환 | `kind=task`에서 `stop_reason=max_tokens` 비율, `output_tokens` 분포가 8192에 얼마나 가까운지 |
| 거절 시 `fallbacks` | `stop_reason=refusal` 비율 |
| 토큰 기준 히스토리 자르기 | `kind=chat`의 `input_tokens`와 `history_messages` 관계, 최댓값 |

텍스트 로그라면 예를 들어 이렇게 센다.

```sh
grep 'claude call kind=task' app.log | grep -o 'stop_reason=[a-z_-]*' | sort | uniq -c
```

확인:

- 테스트 4개 추가, 전체 44개 통과. `claude.usage` 로그를 `ListAppender`로 붙잡아 문구와 key-value를 함께 확인한다 (작업 잘림, 작업 API 오류, 채팅 정상, 채팅 도중 실패).
- 실제 이미지를 임시 Postgres 17과 가짜 API 키로 실행해 작업을 하나 만들었다. 401이 나서 `error=CONFIG` 줄이 텍스트 로그와 ECS JSON(`"duration_ms":881`, `"error":"CONFIG"`) 양쪽에 나오는 것을 확인했다. 확인 후 임시 컨테이너·네트워크·이미지는 삭제했다.
- 실제 Claude 응답의 토큰 수 기록은 실제 API 키가 필요해 mock으로만 확인했다.

## 삭제 API

대화·작업·문서를 지우는 API가 없었다. 세 가지를 추가했다. 모두 성공하면 204, 없으면 404를 돌려준다.

| API | 동작 |
|---|---|
| `DELETE /conversations/{id}` | 대화와 메시지 삭제 (V1의 `on delete cascade`) |
| `DELETE /tasks/{id}` | 작업만 삭제. 문서는 남고 `task_id`만 `null`이 된다 (V1의 `on delete set null`) |
| `DELETE /documents/{id}` | 문서 삭제. 작업은 `DONE`으로 남고 `documentId`만 `null`이 된다. Claude 맥락의 "최근 작성된 문서"에서도 빠진다 |

- 작업을 지울 때 문서는 남기기로 했다(A안). 문서가 결과물이라 작업 목록을 정리하다 잃는 쪽이 더 아깝고, DB 외래 키도 이미 그렇게 되어 있어 마이그레이션이 필요 없다.
- 리포지토리마다 `deleteReturningCount`(JPQL bulk delete)를 두어, 조회 없이 한 번에 지우고 지운 행 수로 404를 판단한다.
- 영구 삭제다. 휴지통(`deleted_at`)과 여러 개 한 번에 삭제는 넣지 않았다.

진행 중인 것을 지울 때:

- **답변 스트리밍 중 대화 삭제:** 전에는 답변을 저장할 때 외래 키 오류가 나서 클라이언트가 `done`/`error` 없이 연결만 끊겼다. `saveAssistant`가 대화 행을 `select ... for update`로 잠근 뒤 저장하게 바꿨다. 대화가 없으면 저장하지 않고 `error` 이벤트(`CONVERSATION_DELETED`)를 보낸다. 잠금 덕분에 저장과 삭제가 겹치면 삭제가 저장 뒤로 밀려 메시지까지 함께 지워진다.
- **처리 중(`RUNNING`) 작업 삭제:** 워커의 `complete()`/`fail()`이 `status='RUNNING' and attempts=:attempts` 조건부 update라 행이 없으면 아무것도 쓰지 않는다. 그래서 삭제가 취소처럼 동작한다. 이미 시작된 Claude 호출은 끝까지 돌아 비용은 나간다. 코드 변경 없이 테스트로 보장했다.
- **claim 직후 삭제:** `poll()`이 claim한 작업을 다시 읽을 때 없으면 예외를 던지던 것을 로그만 남기고 넘어가게 했다.
- **삭제된 대화 ID로 채팅:** 지금처럼 새 대화가 만들어지고 새 ID가 `meta` 이벤트로 간다.

확인: `DeleteApiTest` 4개(대화·작업·문서 삭제와 재삭제 404, 패스코드 없으면 401), `ChatServiceTest`에 스트리밍 중 대화 삭제 1개, `TaskWorkerStopReasonTest`에 처리 중 작업 삭제 1개를 추가했다. 전체 50개 통과.

## 채팅 웹 검색·페이지 읽기

채팅에 Anthropic 서버 도구인 `web_search`와 `web_fetch`를 붙였다. 도구 실행은 Anthropic 서버가 하므로 우리 서버는 도구 정의만 보내고 결과를 스트리밍으로 받는다. 직접 만드는 도구(`create_task` 등)와 문서 작성 작업(Task)에 붙이는 것은 다음 단계로 미뤘다.

- **도구:** `WebSearchTool20260209`(질문당 3회, 위치 KR/Asia/Seoul), `WebFetchTool20260209`(질문당 3회, 페이지당 최대 2만 토큰). 둘 다 Sonnet 5.5에서 동적 필터링(검색 결과를 코드로 걸러 컨텍스트를 줄임)을 지원한다. 더 새 버전(`20260318`)은 응답에 결과 블록을 뺄지 고르는 옵션이 추가된 것이라 지금은 필요 없다.
- **프롬프트:** "최신 정보나 사실 확인이 필요할 때만 검색", "출처 목록은 서버가 붙이니 직접 쓰지 말 것"을 추가했다.
- **출처 표시:** 문서상 검색 결과를 사용자에게 보여줄 때 출처를 함께 표시해야 한다. 스트림에서 웹 검색 인용(`citations_delta`의 `web_search_result_location`)과 읽은 페이지(`web_fetch_tool_result`의 URL)를 모아, 답변 끝에 `**출처**` 마크다운 링크 목록(최대 10개, URL 기준 중복 제거)으로 붙인다. 스트리밍으로도 보내고 저장할 때도 넣으므로 프론트엔드 변경이 필요 없다. 페이지 읽기 인용은 URL이 없는 `char_location`이라 인용 대신 읽은 URL을 출처로 쓴다.
- **`pause_turn` 이어 받기:** 서버 쪽 도구 반복이 한도에 걸리면 응답이 `pause_turn`으로 끝난다. 전에는 모르는 종료 이유로 보고 `INTERRUPTED`로 저장했을 것이다. 이제 SDK `MessageAccumulator`로 모은 응답 전체(검색 블록, `encrypted_content` 포함)를 assistant 메시지로 그대로 붙여 다시 요청한다. 같은 SSE 연결로 이어서 텍스트가 흐른다. 최대 3번까지 이어 받고, 넘으면 받은 만큼 `TRUNCATED`로 저장한다.
  - 모으기(`accumulate`)가 예외를 던져도 답변은 계속 받고 이어 받기만 포기한다. 새 이벤트 종류 때문에 채팅 전체가 깨지지 않게 하려는 것이다.
- **사용량 로그:** 이어 받은 요청까지 토큰을 합치고, 채팅 줄에 `web_search_requests`, `web_fetch_requests`, `continuations`를 붙였다.
- **저장되는 것:** 대화 기록에는 여전히 텍스트(출처 목록 포함)만 저장한다. 다음 질문에서 Claude는 이전 검색 결과 원문 대신 답변 텍스트만 본다. 필요하면 다시 검색한다.
- **배포 체크리스트:** Claude Console에서 웹 검색이 꺼져 있으면 모든 채팅이 400으로 실패하므로 확인 항목과 비용을 추가했다.

테스트: `ChatWebToolsTest` 5개를 추가했다. 기존 테스트는 Mockito mock 이벤트를 쓰는데, 이번 테스트는 SDK의 JSON 매퍼로 실제 API 모양의 이벤트(`message_start` → 블록 시작/델타/끝 → `message_delta` → `message_stop`)를 만들어 `MessageAccumulator`가 실제로 응답을 조립하게 했다(`ChatStreamScript`).

## 채팅에서 문서 작성 맡기기 (`create_task` 도구)

채팅 중 "자소서 초안 맡겨줘" 같은 요청을 Claude가 직접 작업(Task)으로 만들 수 있게, 우리 서버가 실행하는 도구 `create_task`를 추가했다. 확인 없이 바로 만드는 방식(A안)이다. 1인용이고, 잘못 만든 작업은 `DELETE /tasks/{id}`로 지우거나 처리 중에 지워 취소할 수 있다.

- **도구 정의 (`CreateTaskTool`):** 입력은 `instruction`(필수), `context`(선택)이고 `POST /tasks`와 같은 길이 제한이다.
  - 설명에 세 가지를 적었다. 사용자가 긴 문서를 분명히 요청했을 때만 쓸 것, 애매하면 먼저 물어볼 것, 작성자는 대화를 볼 수 없으니 필요한 내용을 `context`에 담을 것.
  - 시스템 프롬프트에도 한 줄을 추가했다.
  - Sonnet 5.5는 `tool_choice`로 도구를 강제하면 400이 나서, 언제 쓸지는 설명으로만 안내한다.
- **흐름:** 응답이 `stop_reason: tool_use`로 끝나면 모은 응답에서 `tool_use` 블록을 찾아 실행한다. 그 응답을 assistant 메시지로 그대로 붙이고, 모든 `tool_use`에 대한 `tool_result`를 user 메시지로 붙여 다시 요청한다. 웹 검색 때 만든 `pause_turn` 이어 받기 반복문을 확장했다.
  - Sonnet 5.5는 도구 호출 사이 문구를 `thinking` 블록으로 보낼 수 있는데, 받은 응답을 통째로 붙이므로 그대로 돌려보낸다.
  - 도구 결과를 돌려주며 이어 받기는 최대 2번이고, 넘으면 `TRUNCATED`로 저장한다.
  - 웹 검색과 함께 불리면 API가 `tool_use`로 먼저 멈추고 다음 요청에서 검색한다. 같은 반복문으로 처리된다.
- **안전장치:**
  - 스트리밍 요청이라 `eager_input_streaming: true`를 켰다. 이 경우 API가 입력을 검증하지 않으므로 서버가 직접 검증한다. 형식 오류, 빈 `instruction`, 길이 초과면 작업을 만들지 않고 `is_error` 결과로 사유를 돌려준다.
  - 답변 하나에 작업은 1개까지만 만든다. 두 번째 호출부터는 오류 결과를 돌려준다.
  - `max_tokens`·`refusal`로 끝난 응답의 도구는 실행하지 않는다. 입력이 잘렸을 수 있기 때문이다. 응답 모으기에 실패한 경우도 실행하지 않는다.
  - 처리하지 않는 도구 이름이 오면 "알 수 없는 도구" 오류 결과를 돌려준다. `tool_use`마다 `tool_result`가 있어야 하기 때문이다.
- **클라이언트:** 작업을 만들면 SSE `task` 이벤트(`{"taskId", "instruction"}`)를 보낸다. 저장되는 답변에는 Claude의 텍스트만 남는다.
- **로그:** 채팅 사용량 줄에 `tool_calls`를 추가했고, 작업을 만들면 대화 ID와 작업 ID를 로그로 남긴다.

테스트:

- `ChatCreateTaskToolTest` 7개를 추가했다. `ChatStreamScript`에 `tool_use` 블록 fixture를 넣었다.
  - 도구 정의
  - 정상 생성: 두 번째 요청에 `tool_use`와 `tool_result`(작업 ID)가 들어가는지
  - 잘못된 입력
  - 두 번 호출
  - `max_tokens`로 끝남
  - 웹 검색과 섞임
  - 이어 받기 한도
- `ChatControllerTest`에 `task` SSE 이벤트 1개를 추가했다.
- 전체 63개 통과. 실제 API로는 확인하지 못했다.

## 기억의 기반 (1단계)

목표는 "나에 대해 계속 이어지는 AI 매니저"다. 그런데 통화는 클라이언트가 Gemini와 직접 연결하고, 서버는 통화를 시작할 때 고정된 맥락만 줬다. 그래서 통화를 끊으면 내용이 사라지고, 통화와 채팅도 서로 몰랐다. 기억을 서버가 갖고, 통화와 채팅은 그 기억을 쓰는 입구가 되도록 1단계를 만들었다.

- **V6:**
  - `conversations`에 `channel`(`CHAT`/`VOICE`), `summary`, `memory_processed_at`, `memory_claimed_at`을 추가했다.
  - 새 테이블 `memories`: `category`는 `FACT`/`PREFERENCE`/`ROUTINE`/`GOAL`/`PROGRESS`/`OTHER`, `content`는 최대 500자, `source_conversation_id`는 대화를 지우면 `null`이 된다.
- **`POST /voice/calls`:** 통화가 끝나면 클라이언트가 받아 적은 기록(`startedAt`, `endedAt`, `turns[{role, text}]`)을 보낸다. 서버는 이를 `VOICE` 대화로 저장한다.
  - 발화는 최대 500개, 하나에 5,000자까지다.
  - 제목은 "통화 11월 3일 21:30"처럼 한국 시간으로 붙는다.
  - 대화 목록에 `channel`을 추가했다.
- **`MemoryWorker`:** 1분마다 최대 5개 대화를 처리한다.
  - 대상: 통화는 저장 즉시, 채팅은 30분 동안 조용할 때. 마지막 추출 이후 새 메시지가 있는 대화만 가져간다.
  - 대화 원문(최대 6만 자)과 기존 기억(최대 200개, id 포함)을 주고, structured outputs(JSON 스키마)로 `{summary, operations[{op, id, category, content}]}`을 받는다. `op`는 add/update/delete이고, 변경과 요약을 한 트랜잭션으로 반영한다.
  - 여러 서버가 동시에 돌아도 같은 대화를 두 번 처리하지 않는다. 작업 워커처럼 `SKIP LOCKED`와 claim 표시를 쓴다.
  - 실패하면 claim을 그대로 둬서 10분 뒤에만 다시 시도한다.
  - 처리 시점으로는 claim할 때 본 `updated_at`을 기록한다. 그래서 추출하는 동안 새 메시지가 오면 다음 실행 때 다시 처리된다.
  - 다시 처리할 때는 기존 기억을 보고 중복 대신 수정·삭제하게 했다.
  - `claude.usage` 로그에 `kind=memory`로 남는다.
- **`SensitiveInfoFilter`:** 프롬프트에서 민감 정보를 빼게 한 데 더해, 저장 직전에 패턴으로 한 번 더 막는다. 걸리면 가리지 않고 통째로 버린다.
  - 막는 것: 주민번호, 카드번호(Luhn 검사), 하이픈으로 나뉜 10자리 이상 숫자(계좌·전화), API 키 형식(`sk-`, `AKIA`, `ghp_` 등), 글자와 숫자가 섞인 32자 이상 토큰, "비밀번호/비번/password" 뒤에 숫자·기호가 섞인 값
  - 날짜(8자리), "비밀번호를 자주 바꾼다", "1Password manager", 점수·문제 번호는 통과시킨다.
  - 요약에 걸리면 요약은 저장하지 않는다.
  - 대화 원문은 지금 채팅처럼 그대로 저장한다(A안).
- **`/memories` API:** 조회(카테고리 필터), 추가, 수정, 삭제. 직접 입력한 내용도 민감 정보면 400으로 거절한다.
- **맥락 반영 (`ContextService`):**
  - 채팅: 기억 전체(최대 200개, 카테고리별)와, 지금 대화를 뺀 최근 대화 요약 5개(통화 포함)를 넣는다.
  - 통화(`GET /context/voice`): 최근 기억 40개와 최근 대화 요약 3개를 넣는다.
  - 채팅 시스템 프롬프트에 "지난 대화에서 기억하는 것을 참고"를 추가했다.
- **엔티티 주의:** `Conversation.summary`는 JPA에서 읽기 전용(`insertable/updatable = false`)으로 매핑했다. 미리 읽어 둔 엔티티를 저장할 때 워커가 쓴 요약을 덮어쓰지 않게 하려는 것이다. 워커 전용 컬럼(`memory_*`)은 엔티티에 넣지 않았다.
- **배포 체크리스트:** 기억 추출 비용과, V6 직후 기존 대화가 모두 처리 대상이 된다는 점(건너뛰는 SQL 포함)을 적었다.

## 말로 동작시키기 (2단계)

1단계로 기억이 서버에 쌓이게 했으니, 2단계에서는 말로 요청한 일을 서버가 처리하게 했다. 채팅(Claude)과 통화(Gemini)가 **같은 도구**를 쓰도록 도구를 서버 한 곳(`ToolRegistry`)에 모았다.

- **V7:**
  - `routines`: 제목, `REMINDER`/`BRIEFING`, 내용, 요일, 시각(한국 시간), 켜짐 여부, 다음 실행 시각, 실행 표시
  - `notifications`: 알림함
  - `activity_logs`: 분류, 내용, 분, 날짜
- **공용 도구 (`AgentTool`, `ToolRegistry`, `ToolInput`):**
  - 도구마다 이름, 설명, JSON 스키마, 답변당 횟수 제한, 실행 함수를 둔다.
  - 입력은 `ToolInput`으로 서버가 직접 검증한다. `eager_input_streaming`이라 API가 검증하지 않기 때문이다.
  - 잘못된 입력, 횟수 초과, 서버 오류는 예외 대신 `ok=false` 결과로 돌려줘서 모델이 고치거나 사용자에게 설명하게 한다.

| 도구 | 동작 | 답변당 |
|---|---|---|
| `create_task` | 문서 작성 맡기기 (기존 것을 옮김) | 1 |
| `save_memory` | 기억 저장 (민감 정보 필터) | 5 |
| `create_routine` | 루틴 등록 | 3 |
| `list_routines` | 루틴 목록과 id | - |
| `update_routine` | 켜기/끄기, 이름·종류·내용·시각·요일 변경 | 3 |
| `delete_routine` | 영구 삭제. 설명에 "이름으로 다시 말해 주고 확인받은 뒤에만" | 3 |
| `log_activity` | 활동 기록 (날짜 생략 시 오늘, 미래 날짜 거절) | 5 |

- **채팅:**
  - `create_task`만 따로 처리하던 반복문을 레지스트리 호출로 일반화했다.
  - 목록을 본 뒤 수정하는 식으로 연달아 쓸 수 있게 도구 이어 받기 한도를 2번에서 4번으로 늘렸다.
  - 작업 외의 도구를 실행하면 새 SSE 이벤트 `action`(`{"tool", "summary"}`)을 보낸다.
  - 시스템 프롬프트에 도구별 사용 안내와 "되돌릴 수 없는 일은 먼저 확인"을 넣었다.
- **통화 (`/tools`):**
  - `GET /tools`: 도구 목록(이름, 설명, `parameters` JSON 스키마)을 준다. 클라이언트가 Gemini 함수 선언으로 등록한다.
  - `POST /tools/{name}` (`{"args": {...}}`): 서버가 실행하고 `{ok, result, error, summary}`를 준다. 도구 실패도 200으로 주고, 없는 도구만 404다.
  - 통화에는 답변 단위가 없어 횟수 제한은 호출마다 새로 센다.
  - 통화 중에는 대화가 아직 저장되지 않아 만든 기록의 출처(`source_conversation_id`)가 비어 있다.
- **`RoutineRunner`:** 1분마다 시간이 된 루틴을 최대 10개 실행한다.
  - `REMINDER`는 문구를 그대로 알림함에 넣는다.
  - `BRIEFING`은 프로필, 기억, 루틴, 최근 활동, 문서를 맥락으로 주고 Claude가 5줄 이내 브리핑을 쓴다(`kind=routine`).
  - 여러 서버에서도 한 번만 실행되게 `SKIP LOCKED`와 claim을 쓴다.
  - 서버가 꺼져 여러 번 밀렸어도 한 번만 실행하고 지금 이후로 넘어간다.
  - 일시적인 오류면 claim을 남겨 10분 뒤 재시도한다. 다시 해도 같은 오류(설정·요청 오류)면 "브리핑을 만들지 못했어요"를 알리고 다음 실행으로 넘어간다.
  - 완료할 때 루틴을 다시 읽어, 실행 중 수정됐으면 바뀐 시각으로 다음 실행을 잡고, 삭제됐으면 아무것도 쓰지 않는다.
- **`RoutineSchedule`:** 다음 실행 시각은 한국 시간과 요일 기준이다. 서버가 UTC여도 같다. 라벨은 "매일 08:00", "월·수·금 22:00" 형식이다.
- **화면용 API:**
  - `GET/POST /routines`, `PUT/DELETE /routines/{id}`: 도구와 같은 `RoutineService` 규칙을 쓴다. 최대 30개다.
  - `GET /notifications?unread=`, `POST /notifications/{id}/read`
  - `GET /activities?from=&to=` (기본 최근 7일), `DELETE /activities/{id}`
- **맥락:** 채팅과 통화에 다음을 넣는다.
  - 읽지 않은 알림 최대 3개와 "그 밖에 N개". 푸시가 없어 AI가 대화 시작 때 먼저 전한다.
  - 켜진 루틴
  - 최근 7일 활동(분류별 건수와 시간, 최근 항목)
  - 통화 맥락에는 쓸 수 있는 도구 안내 한 줄도 넣었다.

테스트:

- 25개를 추가해 전체 124개가 통과했다.
  - `RoutineScheduleTest` 4: 오늘/내일, 요일, UTC 서버, 라벨
  - `ToolApiTest` 7: 목록, 등록, 입력 오류, 끄기·삭제, 활동 날짜, 민감 기억, 404·401

  - `RoutineApiTest` 4

  - `MemoryContextTest` 1개 추가

## 성장 돕기 (3단계)

목표를 세우고, 활동을 목표에 연결하고, 매주 돌아보는 흐름을 만들었다. 숫자(시간 합계, 달성률, 지난주 대비)는 모두 서버가 계산하고, Claude는 해석과 제안만 쓴다. AI가 합계를 틀리게 말하지 않게 하려는 것이다. 푸시 알림은 클라이언트 형태(웹/앱)를 확인한 뒤 3-2단계로 따로 한다.

- **V8:**
  - `goals`: 제목, 설명, 분류, 주간 목표 분, 마감일, 상태(`ACTIVE`/`DONE`/`DROPPED`)
  - `activity_logs.goal_id`
  - `reviews`: 기간, 통계 JSON, 본문, 루틴
  - `routines.kind`에 `REVIEW` 추가
  - **기본 주간 회고 루틴(매주 일요일 21:00 KST)** 삽입. 첫 실행 시각 계산식은 화요일, 일요일 20:59/21:00, 일요일 23:30, 월요일 00:10(UTC로는 일요일)에서 맞는지 Postgres 17로 확인했다.
- **목표 (`GoalService`):**
  - 진행 중인 목표는 최대 10개다. 끝난 목표를 다시 진행 중으로 돌릴 때도 한도를 지킨다.
  - 한 주는 월요일에 시작한다(한국 시간). 이번 주 진행은 목표에 연결된 활동 시간의 합이다.
  - 진행 문구는 "정보처리기사 합격 (D-28): 이번 주 6시간 / 목표 10시간" 형식이고, 마감이 지나면 "마감 2일 지남"으로 쓴다.
- **도구 3개 추가 (총 10개):**
  - `create_goal`: 비슷한 목표가 있으면 새로 만들지 말고 수정하게 안내한다.
  - `list_goals`: 이번 주 진행과 id를 보여 준다.
  - `update_goal`: 상태를 바꾸기 전에 확인받게 안내한다.
  - `log_activity`에 `goal_id`(선택)를 추가했다. 진행 중이 아니거나 없는 목표면 거절한다.
- **주간 회고 (`ReviewService`, `REVIEW` 루틴):**
  - 서버가 지난 7일(오늘 포함, 한국 날짜) 통계를 계산한다.
    - 분류별 시간과 건수, 직전 7일 대비 증감
    - 목표별 시간과 주간 목표 대비 %
    - 기록이 없는 날 수
    - 완료된 문서 작업 수
  - Claude가 통계, 활동 기록(최대 60줄), 전체 맥락을 보고 10줄 이내 회고를 쓴다. 구성은 한 줄 요약, 잘한 점, 아쉬운 점, 다음 주 제안 2~3개다.
  - `reviews`에 저장하고 알림함에도 넣는다.
  - 거절되거나 비면 회고를 저장하지 않고, 통계만 담은 "회고를 만들지 못했어요" 알림을 남긴다.
  - 오류 재시도 규칙은 다른 루틴과 같다. 실패 알림 문구는 "브리핑 작성에 실패했어요"처럼 종류 이름을 넣도록 바꿨다.
- **맥락:**
  - 진행 중인 목표와 이번 주 진행을 넣는다. id도 함께 넣어 `log_activity`의 `goal_id`로 바로 쓰게 했다.
  - 2주 안에 쓴 최근 회고를 넣는다(채팅 1,500자, 통화 400자).
  - 통화용 도구 안내에 목표 도구를 추가했다.
- **기억 추출:** 목표 목록을 함께 주고, 목표와 그 진행은 GOAL·PROGRESS 기억으로 중복 저장하지 않게 했다.
- **API:**
  - `GET/POST /goals`, `PUT /goals/{id}`: 이번 주 분, 남은 날, 진행 문구를 함께 준다.
  - `GET /reviews`, `GET /reviews/{id}`: 통계는 JSON 객체로 준다.
- **정리:** 스트리밍이 아닌 Claude 호출(브리핑, 회고)이 같은 "타임아웃·재시도 제한 + 사용량 로그" 코드를 반복해서 `AnthropicClient.createLogged()`와 `Message.text()`로 묶었다.

- 11개를 추가해 전체 135개가 통과했다.
