## 상세

### 1. Task 응답의 `stop_reason` 미확인 (높음) — ✅ 완료
- 처리: PR #5 (`f279d8b`). 잘림·거절·예상 밖 종료는 재시도 없이 `FAILED`, 빈 본문은 재시도. 자세한 내용은 [2026-11-03.md](2026-11-03.md)의 "잘리거나 거절된 Claude 응답 처리".

- 위치: `TaskWorker.runClaude()`
- 현재: 응답의 텍스트 블록을 이어 붙여 그대로 문서로 저장한다.
- 문제
  - `stop_reason == "max_tokens"`: 8192 토큰에서 잘린 문서가 `DONE`으로 저장된다. `claude-sonnet-5-5`는 thinking이 기본으로 켜져 있고 thinking도 `max_tokens` 안에서 쓰기 때문에, 긴 문서에서 잘릴 가능성이 있다.
  - `stop_reason == "refusal"`: 거절 응답(빈 텍스트나 짧은 안내)이 문서로 저장된다.
- 제안: `end_turn`이 아니면 예외를 던져 기존 재시도·실패 경로를 타게 한다. `max_tokens`는 한도를 늘리거나 streaming으로 바꾸는 것도 검토한다.

### 2. 채팅 실패 시 히스토리 불일치 (높음)
- 위치: `ChatController.chat()`, `ChatService.prepare()`
- 현재: 사용자 메시지를 먼저 저장하고, assistant 응답은 스트리밍이 끝난 뒤에만 저장한다.
- 문제: Claude 오류, `SseEmitter` 타임아웃(180초), 브라우저 연결 끊김이 생기면 사용자 메시지만 남는다. 다음 요청에서는 user 메시지가 연속으로 들어가고, 화면의 대화 목록과 실제 기록도 어긋난다.
- 제안: 실패하면 부분 응답을 `[중단됨]` 표시와 함께 저장하거나, 사용자 메시지를 롤백한다. 채팅도 `stop_reason`을 확인한다.

### 3. 제목만 필요한데 본문까지 조회 (중간)
- 위치: `ContextService.recentDocTitles()`, `TaskController.documents()`
- 현재: `findTop50ByOrderByCreatedAtDesc()`로 `content`(text)까지 포함한 문서 50개를 읽은 뒤 제목 5~10개만 쓴다. `forClaude()`는 채팅과 작업마다 호출된다.
- 제안: 제목만 읽는 projection 쿼리(`select id, task_id, title, created_at ... limit :n`)를 쓰고, `documents(created_at)` 인덱스를 추가한다.

### 4. `GET /tasks`의 N+1 조회 (중간)
- 위치: `TaskController.toDto()`
- 현재: `DONE` 작업마다 `findByTaskId`를 호출해, 최대 20번 추가로 조회한다. 이때 문서 본문도 함께 읽는다.
- 제안: 작업 ID 목록으로 문서 ID를 한 번에 조회(`where task_id in (...)`)하거나, 조인 쿼리로 바꾼다.

### 5. 테스트 범위 (중간)
- 현재 테스트는 `contextLoads`와 `TaskWorkerConcurrencyTest`뿐이다.
- 추가 후보
  - 패스코드 필터: 헤더 없음 → 401, OPTIONS는 통과
  - `POST /chat` SSE 이벤트 순서(`meta` → `delta` → `done`)와 실패 시 `error` 이벤트
  - `ChatService.prepare()` 히스토리가 항상 user 메시지로 시작하는지
  - `recoverStale()`의 `MAX_ATTEMPTS` 도달 시 `FAILED` 처리

### 6. 패스코드 비교 방식 (낮음)
- 위치: `WebConfig.passcodeFilter()`
- 현재: `req.getHeader("X-App-Passcode") == passcode`
- 제안: `MessageDigest.isEqual`로 상수 시간 비교를 한다. 실제 공격 가능성은 낮지만 수정 비용이 거의 없다.

### 7. 예외 메시지 노출 (낮음)
- 위치: `ChatController`의 `error` 이벤트, `tasks.error` 컬럼(`GET /tasks`로 반환)
- 현재: SDK·DB 예외 메시지가 그대로 응답에 들어간다.
- 제안: 클라이언트에는 일반 메시지만 보내고, 자세한 내용은 로그로 남긴다.

### 8. 입력 길이 제한 없음 (낮음)
- 위치: `CreateTaskRequest`, `ChatRequest`, `UpdateProfileRequest`
- 문제: 아주 긴 입력이 그대로 프롬프트에 들어가 비용이 커지거나 컨텍스트 한도를 넘을 수 있다. `type`도 자유 문자열이다.
- 제안: `@Size` 제약을 추가하고, `type`은 enum으로 바꾸거나 허용 값을 검사한다.

### 9. 재시도할 수 없는 오류도 재시도 (낮음) — 일부 완료
- 위치: `TaskWorker.poll()`의 실패 경로
- 처리됨 (#5): 재시도 없이 실패시키는 경로(`NonRetryableTaskException`, `fail(..., retryable = false)`)를 만들었고, 잘림·거절 응답에 적용했다.
- 남은 것: SDK 예외 중 400·401·404처럼 다시 해도 같은 결과가 나오는 오류도 이 경로로 보내기. SDK의 예외 타입으로 구분할 수 있다.

### 10. Postgres 버전 불일치 (낮음)
- `compose.yaml`은 `postgres:17`, `TestcontainersConfiguration`은 `postgres:16-alpine`을 쓴다.
- 제안: 운영 DB 버전에 맞춰 두 곳을 통일한다.

### 11. Docker 컨테이너 root 실행 (낮음)
- 위치: `Dockerfile` 실행 단계
- 제안: 전용 사용자를 만들고 `USER`로 지정한다.

### 12. 코드 정리 (낮음)
- `config/webConfig.kt` 안의 클래스 이름은 `WebConfig`라서 파일명과 대소문자가 다르다.
- `ProfileController`는 `Profile.kt`, `ContextController`는 `ContextService.kt` 안에 있다. 다른 모듈처럼 컨트롤러 파일을 분리하면 찾기 쉽다.
